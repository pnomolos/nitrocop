# Should nitrocop build a project index for ProjectIndexHelp cops?

Investigated read-only in `nitrocop-wt-newcops` (branch `cops/rubocop-1.91-batch-1`, vendor/rubocop v1.91.0).

## 1. Upstream semantics

`ProjectIndexHelp` (`vendor/rubocop/lib/rubocop/cop/mixin/project_index_help.rb:13-186`) is a thin query/helper layer over `Cop::Base#project_index`. RuboCop itself does **not** implement the index — it defers entirely to an optional external gem, **`rubydex`** (`Rubydex::Graph`), loaded defensively:

- `vendor/rubocop/lib/rubocop/project_index_loader.rb:11-64`: `ProjectIndexLoader.available?` requires Ruby ≥3.2 and `require 'rubydex'` to succeed; not a runtime dependency of rubocop itself. `build_index(paths)` = `Rubydex::Graph.new; graph.index_all(paths); graph.resolve`.
- Opt-in only: `AllCops/UseProjectIndex: false` by default (`vendor/rubocop/config/default.yml:115`). `ProjectIndexIncludesGems: false` (line 121) controls whether bundled gem sources are indexed too.
- Population (`runner.rb:78,120-146`): built once per `run`, from **all target files found from the config's `base_dir_for_path_parameters` root**, unioned with the current run's target files and (optionally) bundled gem `.rb` sources — i.e. the whole project, not just files under lint in this invocation (`runner.rb:131-141`, comment: "cross-file offenses must not depend on which files happen to have changed"). Built before parallel dispatch, in the main process.
- Invalidation/caching: `ProjectIndexHelp#external_dependency_checksum` (`project_index_help.rb:28-34`) hashes a per-run **single-entry memoized** signature (`cached_index_signature`, class-level `attr_accessor`, keyed by `index.equal?`) built by stat'ing every indexed file (`compute_project_index_signature`, lines 170-185: `mtime,size` per file, sorted, joined). This checksum feeds into `ResultCache`'s per-file key: `result_cache.rb:268` — `keys = [team.external_dependency_checksum, ...]`. So **any indexed file changing invalidates every file's cache entry project-wide**, even ones unrelated to the change — a coarse, all-or-nothing invalidation despite being computed carefully.
- `--parallel`: index build happens in the main process before fan-out (`runner.rb:78`); the resolved graph is then assigned onto every cop instance per team (`runner.rb:704-708`, `cop.project_index = @project_index`). Parallel inspection is disabled only on Windows when an index is present (`runner.rb:240-249`) — elsewhere parallel + index coexist because the graph is read-only during inspection.
- Stores: method definitions with full arity/keyword signatures (`Rubydex::MethodDefinition`/`Signature`, arity math in `indexed_method_arity.rb:32-91`), constants/namespaces with resolved ancestry (`Rubydex::Namespace`, `resolve_constant`, `ancestors`, `find_member`), singleton-class members, YARD `@deprecated` tags (`deprecated_reference.rb`), and whole-project method-reference sites including string/symbol heuristics for `send`/DSL calls (`unused_private_method.rb`).
- The 5 cops' queries all gate on `project_index` being non-nil and have **no local-file fallback** — see §3.

Cops and their exact index calls:
- **Lint/ArgumentMismatch** (`lint/argument_mismatch.rb:65-95`): `checkable_call?` requires `project_index && node.receiver&.const_type? && !node.method?(:new)`; resolves receiver via `resolve_constant_in_index`, requires `fully_resolved_index_ancestry?`, gets singleton member shape via `indexed_singleton_member` + `IndexedMethodArity#indexed_member_shape`.
- **Lint/SuperArgumentMismatch** (`lint/super_argument_mismatch.rb:70,132`): looks up `project_index[lexical_nesting_of(def_node).join('::')]`, compares `super`'s args against the resolved ancestor's overridden signature.
- **Lint/NameTypo** (`lint/name_typo.rb:78-266`): for constants, `resolve_constant_in_index(node.namespace)` + `complete_index_members?` (full ancestry resolved and namespace not gem-owned) then `DidYouMean::SpellChecker` against `namespace.members`; for methods, same resolution + `unknown_method_owner` + spell-check against `method_member_names` (which walks `declaration.ancestors` for singleton members too). Also cross-references bundled gem names via `config.gem_versions_in_target`/`path_sourced_gems_in_target` to suppress gem-owned namespaces.
- **Lint/DeprecatedReference** (`lint/deprecated_reference.rb`): resolves bare/`self` calls and receiver-qualified calls against the index, checks YARD `@deprecated` tags on the resolved definition, and constants via `project_index['Object']`/namespace resolution.
- **Lint/UnusedPrivateMethod** (`lint/unused_private_method.rb:113-166`): `project_index.method_references` — a whole-project reverse-reference set including string/symbol-literal heuristics — cross-checked per private method; a **single-entry class-level cache** (`cached_reference_names`) mirrors the `ProjectIndexHelp` pattern.

Three *already-enabled* cops also mix in `ProjectIndexHelp` but **degrade gracefully** when `project_index` is nil (their non-indexed behavior is what nitrocop implements today and matches oracle 1:1): `Lint::ConstantResolution` (`return if project_index && !ambiguous_resolution?`), `Lint::DuplicateMethods` (`return unless project_index` guards only the *extra* cross-file check), `Lint::MissingSuper` (same pattern). The 5 cops in question have **no such fallback** — each starts with a hard `return unless project_index`.

## 2. nitrocop architecture fit

- `src/linter.rs:247-270` (`run_linter`): single `rayon` `par_iter()` over `discovered.files`, each file parsed independently inside `lint_file` (Prism `ParseResult` is `!Send`, per AGENTS.md — confirmed, parse happens per-thread). No cross-file state exists today except the per-cop `Cop: Send + Sync` trait (`src/cop/mod.rs:271-379`) and the `ResultCache` (`src/cache.rs`), which is keyed by path + content + a config/session digest (`cache.rs:106-144,366-394`) — no notion of "signature of the whole file set."
- `src/cop/variable_force/` (4,318 LOC) is the closest existing analog: a single shared AST-walk **per file** producing a `VariableTable`, delivered to cops via `VariableForceConsumer` hooks (`mod.rs:44-122`). It proves the "shared pre-pass + trait hook" pattern nitrocop already uses, but it is **intra-file only** — it runs inside the same rayon task as the cop checks, after `check_source`/before node walk, for one file at a time. A project index is fundamentally different: it needs data from *every* file before *any* file can be checked, which VariableForce's per-task model cannot provide.

### Proposed minimal design
1. **Extraction pass** (new, e.g. `src/cop/project_index/extract.rs`): walk each file's Prism AST once, producing a `Send + Sync` `FileSymbols` struct (namespace defs with superclass/mixin refs as strings, method defs with positional/keyword arity shape mirroring `IndexedMethodArity`, YARD `@deprecated` doc-comment scan, and a set of string/symbol literal "possible reference" names for `UnusedPrivateMethod`). No Prism nodes retained — only owned Rust data (Strings, enums, ranges).
2. **Aggregation pass** (`src/cop/project_index/graph.rs`): merge all per-file `FileSymbols` into one `ProjectIndex { namespaces: HashMap<String, Namespace>, ... }`, resolve constant nesting/ancestry, resolve method dispatch order — essentially a from-scratch reimplementation of `Rubydex::Graph`'s resolve step (constant nesting rules, MRO with mixins, singleton-class linkage). This is the bulk of the work; `rubydex` itself is a nontrivial standalone gem, not a rubocop-internal file.
3. **Wiring**: `run_linter` runs the extraction pass over `discovered.files` with its own `par_iter()` (a *second* full parse of every file, since the index must be complete before any cop's `check_source` call — cops need to query already-resolved ancestries mid-file-check, so this cannot be folded into the existing per-file pass), builds the `Arc<ProjectIndex>`, then proceeds with the existing per-file rayon fan-out, handing the `Arc` down through `lint_file` → `cop.check_source_with_index(..., index: &ProjectIndex, ...)`. New trait hook on `Cop` (default no-op, mirroring `as_variable_force_consumer`): `fn needs_project_index(&self) -> bool { false }`. The pass only runs if `cop_filters` show at least one active cop needing it (checked once via `base_configs`/registry before the extraction loop).
4. **Cache**: cache key must include a project-wide signature (mtime+size per indexed file, like upstream `compute_project_index_signature`) whenever any index-consuming cop is active — otherwise stale cross-file offenses. Simplest correct approach: compute the index-file-set signature once, fold its hash into `ResultCache::new`'s session key (`cache.rs:106`) rather than per-cop granularity — coarser than upstream (upstream still invalidates the *whole* cache on any indexed-file change too, per §1, so this loses nothing).

### Cost estimate
- Extraction + graph resolution (namespaces, ancestry, method arity, YARD deprecation, reference-name harvesting): ~1,500-2,500 LOC (comparable to or larger than `variable_force/`, which is 4,318 LOC for a *simpler*, intra-file-only problem — full MRO/ancestry resolution with mixins and gem-boundary handling is materially harder).
- 5 cops on top of the index: ~150-400 LOC combined (thin, per `IndexedMethodArity`'s 92 LOC and `ArgumentMismatch`'s 99 LOC upstream) — cheap *if* the index exists.
- Wall-clock: a second full parse+walk of every target file before the main pass (extraction is AST-walk-only, no per-cop dispatch, so cheaper than a full lint pass, but still O(files) parse cost — Prism parsing is the dominant cost in nitrocop's profile generally). For the corpus's ~5,500 repos this roughly doubles the AST-construction cost project-wide, only when an index-consuming cop is enabled (opt-in preview tier keeps this off by default, see §3).
- **Ordering constraint is the crux**: cops need the *complete, resolved* index before checking any file (ancestry resolution requires seeing every class reopening across every file first), so this is unavoidably two full passes — no way to interleave with the existing single-pass-per-file architecture.

## 3. Corpus impact

- All 5 cops are **absent from the current oracle artifact** (`by_cop` in `corpus-results.json` has no entries for `Lint/ArgumentMismatch`, `Lint/DeprecatedReference`, `Lint/NameTypo`, `Lint/SuperArgumentMismatch`, `Lint/UnusedPrivateMethod` — confirmed via direct lookup), consistent with the RuboCop version bump landing after the oracle run (`run_date: 2026-09-19T03:09:12Z`).
- Proxy volumes pulled from the same artifact (single-file cops, not true cross-file comparables, but the closest available signal for "how often does this shape of issue occur"): `Lint/UnusedMethodArgument` 26,799 offenses / 2,292 repos; `Lint/DuplicateMethods` (already index-aware but degrading gracefully today) 4,745 / 713 repos; `Lint/MissingSuper` (same) 13,925 / 1,272 repos; `Lint/ConstantResolution` (same) 3,972,535 / 5,546 repos. None of these are true proxies for cross-file arity/typo/dead-code detection — no such cop exists in the corpus today to extrapolate from.
- **Critical finding: the oracle's own RuboCop reference would report zero offenses for all 5 cops even after the version bump**, independent of nitrocop:
  - `bench/corpus/baseline_rubocop.yml` sets `NewCops: enable` (covers the 4 `pending` cops) and explicitly flips several `Enabled: false` cops to `true` (lines 41-58) but **does not set `AllCops/UseProjectIndex: true`**.
  - `bench/corpus/Gemfile`/`Gemfile.lock` do **not** include the `rubydex` gem (grepped, no match) — `ProjectIndexLoader.available?` (`project_index_loader.rb:18-22`) would return `false` even if `UseProjectIndex` were set, per repo, in the per-repo `bundle exec rubocop` invocation used by the oracle (`.github/workflows/corpus-oracle.yml:314-320`, no `--parallel` flag, `--cache false`, per-repo `bundle exec`).
  - Given `checkable_call?`/`check?`/etc. all hard-`return unless project_index` (confirmed in §1), the reference RuboCop run in the oracle produces **0 offenses for these 5 cops as currently configured**, regardless of how many repos would trigger them under a real `UseProjectIndex: true` + `rubydex`-installed setup.
  - Consequence: if nitrocop implemented these cops today (even correctly matching upstream semantics), every single offense nitrocop reports would show as a **false positive against the oracle**, because the oracle baseline never turns on the index. Implementing without first updating `baseline_rubocop.yml` (+ corpus `Gemfile` + accepting the parallel/cache implications) would look like a severe regression, not progress.
  - By contrast, the 3 *already-implemented* index-aware cops (`Lint/ConstantResolution`, `Lint/DuplicateMethods`, `Lint/MissingSuper`) are `perfect_match`/`exercised: True` in the oracle specifically *because* nitrocop implements only their non-indexed fallback path, which is exactly what the oracle's non-indexed RuboCop reference also executes — same code path on both sides.

## 4. Recommendation

**Option B (leave unimplemented) is the right call for now.** Rationale:
- 4/5 cops are `pending` and 1/5 is `Enabled: false` upstream — RuboCop users get none of them without opting in twice (enabling the cop *and* `UseProjectIndex` *and* installing `rubydex`). The population of real users affected today is ~zero.
- The oracle cannot even validate an implementation yet: `baseline_rubocop.yml` + corpus `Gemfile` would need `AllCops/UseProjectIndex: true` and the `rubydex` gem added first, which is itself a nontrivial, separate corpus-infra change (affects per-repo `bundle install`, possibly per-repo build cost across ~5,500 repos, and needs its own signal on whether `rubydex`'s resolution semantics are even stable/reliable enough to trust as ground truth).
- Building the index component (Option A) is a large, high-risk undertaking: ~1,500-2,500+ LOC reimplementing a constant/method-resolution graph (ancestry, MRO, singleton classes, gem-boundary detection, YARD tag parsing) that upstream itself outsources to a whole separate gem (`rubydex`) rather than owning in rubocop-core — that alone signals this is not "one more cop," it's a new analysis subsystem. It also forces a second full-project parse pass (architectural first for nitrocop) and a coarser cache-invalidation scheme.
- Cost of Option B: five `pending`/`disabled`-by-default cops stay unimplemented; `src/rules.rs`/`--rules` output will show them as not-implemented, which is accurate and matches their upstream opt-in status.

**Suggested trigger for revisiting:** (1) `bench/corpus/baseline_rubocop.yml` gains `UseProjectIndex: true` and `rubydex` is added to the corpus bundle (giving real FP/FN signal instead of the current zero-signal state), **and** (2) real-world adoption signal — e.g. `AllCops/UseProjectIndex: true` appearing in a nontrivial slice of corpus repos' own `.rubocop.yml` (currently unknown/unmeasured — worth a quick grep across `bench/corpus/manifest.jsonl`-referenced configs as a cheap leading indicator before committing to the graph-builder work).
