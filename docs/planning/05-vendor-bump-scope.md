## 4. rubocop-ast

**Not required by dependency resolution**: `rubocop.gemspec` pins `rubocop-ast >= 1.49.0, < 2.0` identically at both v1.84.2 and v1.91.0. `rubocop-rails` 2.37.0 wants `>= 1.44.0`, `rubocop-performance` 1.27.0 wants `>= 1.47.1` — vendor's current `v1.49.1` satisfies everything.

**Recommend bumping anyway** (vendor is reference-only, mirrored by hand into `src/cop/shared/{method_dispatch_predicates,access_modifier_predicates,method_identifier_predicates}.rs` etc., per `AGENTS.md`). Latest tag is `v1.50.0`; its changelog (`logs/ast-new-entries.md`) has real semantic bug fixes:

- `Node#argument?` returned `true` for a receiver structurally equal to an argument (e.g. the receiver in `foo.bar(foo)`).
- `Node#chained?` and `MethodDispatchNode#block_literal?` had the same structural-equality false-positive for `foo.bar(foo)`-shaped code.
- `each_when`/`each_in_pattern`/`each_condition`/`each_branch` blockless form returned an unusable `Enumerator` (deprecated methods, unlikely to matter).
- `ProcessedSource#preceding_line` returned the wrong line for first-line tokens.
- Perf-only changes (allocation reduction, Prism-by-default for Ruby 3.3) — no semantic port needed.

Action: since `access_modifier_predicates.rs`'s header literally cites `method_dispatch_node.rb`'s `block_literal?`, diff nitrocop's Rust implementation against `vendor/rubocop-ast` at `v1.50.0` for the `foo.bar(foo)` structural-equality case specifically — if the Rust port doesn't already reference identity/position instead of structural equality, this is a latent, previously-undetected FP source independent of the gem bump.

## 6. Recommended execution order

**Dependency check**: rubocop-rails 2.37.0 requires `rubocop >= 1.89.0`; rubocop-performance 1.27.0 requires `>= 1.89.0`; rubocop-rspec 3.10.2 requires `~> 1.86, >= 1.86.2`. All four are satisfied simultaneously by rubocop 1.91.0 — **no forced staging order**; bump all four vendor submodules in one commit/PR. Splitting them risks a `bench/corpus/Gemfile.lock` that bundler re-resolves inconsistently with whichever vendor tags are half-bumped.

**Suggested single PR**:
1. `git -C vendor/<gem> fetch --tags` (already done) then advance each submodule pointer to its target tag (`v1.91.0`, `v2.37.0`, `v3.10.2`, `v1.27.0`; optionally `vendor/rubocop-ast` to `v1.50.0` per §4).
2. Bump version strings per §1 (`README.md`, `bench/corpus/Gemfile`, `bench/synthetic/Gemfile`, `bench/corpus/diff_results.py`, `src/resources/baseline.json`).
3. Regenerate `src/resources/baseline_cops.json` to add the 23 new cop names (no existing tool does this — write a one-off script reading `vendor/*/config/default.yml` `Enabled` values, or hand-edit).
4. `cd bench/corpus && BUNDLE_PATH=vendor/bundle bundle install`; same for `bench/synthetic`.
5. `uv run ruff check bench/corpus/diff_results.py scripts/dispatch_cops.py bench/corpus/update_readme.py`.
6. `cargo test --release` — this is the real gate: it runs every cop's fixtures directly (`check_source`, bypassing config resolution) against the *old* golden expectations for all ~280 rubocop-touched cops, ~10 rails/rspec/performance cops. Expect failures concentrated in the fixtures tied to the quirk-doc comments in §2 (crash-replication tests for `LiteralAsCondition`, `HashAlignment`, `IndentationWidth`) — those need the fixture + doc comment updated together (TDD, per AGENTS.md), not silently patched.
7. Do **not** run `check_cop.py` or `bench_nitrocop conform` locally (CI-only / explicitly discouraged for routine work). After merge, let the corpus-oracle CI workflow regenerate `corpus-results.json`, then triage the diff with the `triage` skill.

**New/unimplemented cop handling**: confirmed via `src/config/mod.rs::compute_skip_summary` — a cop enabled by config is classified `unimplemented` if it's in `rubocop_known_cops`/`require_known_cops` (sourced from `baseline_cops.json`) but has no `CopRegistry` entry; it's `outside_baseline` if it's in neither. If `baseline_cops.json` isn't regenerated (step 3), the 23 new cops read as `outside_baseline` (looks like a typo/custom cop) instead of `unimplemented` (looks like a known gap) in `--migrate`/`doctor` output — a UX regression, not a crash. **No test asserts 100% cop-implementation coverage**: `tests/integration.rs`'s `migrate_*`/`strict_*` tests all use small synthetic single-cop configs (`Custom/FakeCop`, `Layout/TrailingWhitespace`), not full-registry assertions, so the new unimplemented cops won't fail CI by themselves — they'll simply surface as new FN rows once the corpus oracle runs with `NewCops: enable` (already set in `baseline_rubocop.yml`), to be picked up as ordinary follow-up cop-implementation work, out of scope for the bump PR itself.
