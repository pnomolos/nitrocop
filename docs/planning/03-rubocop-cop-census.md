# RuboCop core + plugin cop census (Part 2)

Generated by `census.py` (this directory) against the vendored submodules
pinned in this repo: `vendor/rubocop` (v1.84.2), `vendor/rubocop-rails`
(v2.34.3), `vendor/rubocop-rspec` (v3.9.0), `vendor/rubocop-performance`
(v1.26.1), `vendor/rubocop-rake` (v0.7.1), `vendor/rubocop-factory_bot`
(v2.28.0), `vendor/rubocop-rspec_rails` (v2.32.0).

**Cop-file detection heuristic:** a file counts as a concrete cop iff it
contains a top-level `class X < Base` (or `< Cop`, walking through
`RuboCop::RSpec::Base` / `RuboCop::FactoryBot::Base`-style subclassing) where
`X` isn't itself `Base`/`Cop`. This naturally excludes `mixin/`, `utils/`,
`legacy/`, `correctors/`, `generator/`, `variable_force/` infra files and
aggregator files like `rspec_cops.rb` (they never match the regex), without
needing an explicit exclude-list. `RuboCop::InternalAffairs` (RuboCop linting
its own source) is included as its own department since it's a real,
shippable cop set, but it's not part of the department list you'd run against
user code — treat it as a bucket-shape data point, not a target department.

**Bucket methodology:** `code_loc` = non-blank, non-`#`-comment lines inside
the file with all `def_node_matcher`/`def_node_search` bodies stripped out
first (so a huge multi-line pattern doesn't inflate "procedural logic" LOC).
`n_matchers` = count of `def_node_matcher`/`def_node_search` calls in the
file. Bucket:
- **A** — `n_matchers >= 1` and `code_loc <= 25`
- **B** — (`n_matchers >= 1` and `25 < code_loc <= 80`) or (`n_matchers == 0` and `code_loc <= 80`)
- **C** — `code_loc > 80`, regardless of matcher count

This is a size/shape proxy, not a semantic judgment — e.g. a cop with zero
matchers but only 40 lines of straightforward config-driven logic still lands
in B. Full per-cop values are in `cops.csv`.

## Overall totals

- **957** concrete cop files analyzed across 7 gems.
- **949** `def_node_matcher`/`def_node_search` pattern strings extracted from those files (heredoc and inline-string forms).
- Bucket split (all gems combined): **A 119 (12.4%)**, **B 668 (69.8%)**, **C 170 (17.8%)**.

**rubocop-rspec note:** the AGENTS.md brief for this census flags that
rubocop-rspec uses its own `Base` (`vendor/rubocop-rspec/lib/rubocop/cop/rspec/base.rb`,
subclassing `RuboCop::Cop::Base` and mixing in `RuboCop::RSpec::Language`) and
`send_pattern`/`block_pattern` helpers. In the vendored version (3.9.0),
`send_pattern`/`block_pattern`/`numblock_pattern` are **deprecated and no
longer present** (confirmed via `CHANGELOG.md`) — they were replaced by
writing plain `def_node_matcher` patterns that call into
`RuboCop::RSpec::Language`'s own node-pattern predicates (e.g. `#rspec?`,
`#ExampleGroups.all`) via the `#method` predicate-call syntax. Those
`Language` module patterns themselves live in
`vendor/rubocop-rspec/lib/rubocop/rspec/language.rb`, not under `cop/rspec/`,
so they aren't counted in the per-cop `cops.csv` rows above, but every
`RSpec` cop that calls `#rspec?`/`#ExampleGroups.all`/etc. is transitively
depending on that shared pattern module — a translator targeting
rubocop-rspec needs to resolve those cross-file predicate calls, not just
per-cop patterns.

`AutoCorrector` dominating (713 of 957 files touch it, ~75%) reflects that
`extend AutoCorrector` is itself detected as an "extend" mixin — it's the

cops still need source-range stitching that a pure NodePattern IR wouldn't
capture on its own.

(Note: `type predicate ?` overlaps with `nil?`/`true?`/`false?` counts since
they share the trailing-`?` shape; treat it as an upper bound on bare type
predicates like `str?`/`send?`, not a disjoint category.)

**Decision-relevant reading:** captures, rest, unions, wildcards, `nil?`, and
symbol/type literals are each used in **~50-70%** of all patterns — an
interpreter that only handles those (roughly nitrocop's current "Phase 1"
interpreter scope per `src/node_pattern/interpreter.rs`) would structurally
match the *majority shape* of most patterns, but would still need to resolve
`#method?` predicate calls (used in **21%** of patterns — not rare) to avoid
just being "optimistically true" on 1 in 5 patterns. Unordered `<>` (6.7%)
and parent/descend refs (`^`/`` ` ``, ~2.5% each) are individually small but
non-trivial in absolute terms (64, 24, and 23 patterns respectively) and are
**completely unimplemented** in the current interpreter (parent/descend
always-true; `<>` has no grammar support at all) — see
`census/nitrocop-internals.md` Part 1.

## Files in this directory

- `census.py` — the script that produced this census (re-runnable: `python3 census.py` from this directory, no dependencies beyond stdlib).
- `cops.csv` — one row per cop file: `gem, dept, name, loc, n_matchers, hooks, mixins, autocorrect, uses_source_text, uses_config, bucket, path`. `hooks` and `mixins` are `|`-joined.
- `nodepattern_features.csv` — one row per NodePattern feature with pattern-count and total-occurrence tallies.
- `census_summary.json` — the aggregate JSON this file's tables were rendered from.
